# 实现前真正需要明确（不再变化）的是会影响外部语义、事后很难兼容修改的部分
例如：

- 一个 job 最终只能产生一个 completion；
- 任一 block 失败时整个 job 失败；
- drain 返回后绝不再访问 primary memory；
- 不做跨重启恢复；
- scheduler 线程不能被普通 I/O 阻塞；
- load 不能被 store 永久饿死。

比如下面这些属于实现细节，不必现在强行出一个结论：

- 是否使用 header；  
    -具体 alignment 如何查询；  
    -内部计数使用哪个 C++ 类型；
- queue capacity 是 `2×QD` 还是 `4×QD`；  
    -CQE 映射表使用 vector 还是 hash table；  
    -一次 submit 凑多少 SQE；  
    -构造期和 job admission 分别放哪些防御性检查。

更实际的推进方法是：

1. 先确定外部契约和关键不变量。
2. 写最小 data engine 骨架。
3. 每遇到一个必须选择的问题，就记录为 design decision。
4. 同时为这个选择增加测试或断言。
5. 性能数据出现前，允许修改内部实现，但不改变外部语义。

# 以上强调的是单需求的实现推进，下面讲的是不同需求之间的衔接

迭代无需预留，比如我们的新需求是给uring-slab加上检查代码

那么这个检查代码我们应当作为一个纯粹的新需求来设计，而不是要求原本的uring-slab代码提供支持。原有的设计应该作为背景被阅读，也就是我们的**系统故事**。
